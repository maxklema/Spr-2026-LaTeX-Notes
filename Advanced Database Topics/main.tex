\section{Lecture 1 - Fundamental Concepts of Database Management}
\vspace{11pt}

\subsection{Applications of Database Technology}
\vspace{11pt}

\textbf{Data in the Real World}
\vspace{11pt}

Data is everywhere, appearing in various forms and sizes. This includes:
\begin{itemize}
    \item Traditional data: Traditional numeric and alphanumeric data in an application
    \item Text data: Documents, emails, and social media posts
    \item Multimedia data: images, audio, and video files
    \item Spatial, temporal data: Geographical, location-based, and time-related information
    \item Volatile data: High-frequency, real-time data
    \item Big Data: large and complex data sets.
\end{itemize}

These data types require effective storage and management using suitable data management techniques.

\vspace{11pt}
\textbf{Applications of Database Technology}
\vspace{11pt}

There are many applications of Database Technology. They can include, but are not limited to: Traditional Business Applications (Structured numeric and alphanumeric data - inventory, payroll, accounting systems), Multimedia Applications (Storage and retrieval of images, audio, and video - e.g,. YouTube, Spotify), Geographical Information Systems (GIS) (Management and analysis of spatial and located-based data - Google Maps), Financial Applications (High-volume, rapidly changing data with strict consistency requirements - like investment banking systems), Sensor-Based Applications (Continuous data streams from sensors - e.g., environmental monitoring, automated shutdown systems), Biometric Applications (Management of biological identifiers - fingerprints, facial or retina scans), Wearable and IoT Applications (Personal and real-time activity data - Fitbit, Apple Watch), Big Data Applications (Large-scale data collection and analytics - retailer point-of-sale and transaction systems).

\vspace{11pt}
\subsection{Key Definitions}
\vspace{11pt}

A Database is a collection of related data organized to support a specific business process or problem domain. A database is designed for a target group of users and the applications that access the data.

A Database Management System (DBMS) is a software system used to define, create, store, manipulate, and maintain a database. A DBMS is composed of multiple software modules, each supporting different database functions.

A Database System is the combination of a database and its DBMS, which often includes database programs/tools and users.

\vspace{11pt}
\subsection{File vs. Database Approach to Data Management}
\vspace{11pt}


\vspace{11pt}
\textbf{File-based Approach to Data Management}
\vspace{11pt}

\begin{center}
    \includegraphics[width=0.5\textwidth]{1.jpg}    
\end{center}

In a file-based approach to data management, each application maintains its own data files, even when storing the same data. An application may access one or multiple files, and data files store only raw data, without metadata or structured definitions.

Data definitions and descriptions are embedded separately within each application, and, as a result, as the number of applications grows, this approach leads to major data management problems.

Here are Seven Problems related to the File-based Approach
\begin{itemize}
    \item Data Redundancy - The same information is stored multiple times across different files.
    \item Data Inconsistency - Duplicate data may become inconsistent when updates are not synchronized.
    \item Strong Application-Data Dependence - Data structure changes require modifications to application programs.
    \item Duplicate Access Logic - Each application defines its own queries and access procedures. Similar procedures are repeatedly implemented across applications.
    \item Poor Maintainability - Systems are difficult to update, manage, and scale over time.
    \item Limited Concurrency Control - Hard to support safe simultaneous access by multiple users.
    \item Difficult Integration - Integrating applications across departments or organizations is challenging.
\end{itemize}

\begin{center}
    \includegraphics[width=0.5\textwidth]{2.jpg}  
\end{center}
\vspace{11pt}

Note: Raw data and Catalog data (metadata, permissions, users, etc.) are a part of the DBMS.

All data is stored and managed centrally by a DBMS, and applications interact directly with the DBMS, not with individual files. The DBMS retrieves and delivers data in response to application requests. 

The DBMS can manage two types of data: Raw data (actual stored data) and Metadata (data definitions and descriptions). Metadata is centrally managed by the DBMS, rather than embedded in applications (Key difference from the file-based approach)

\vspace{11pt}
\textbf{Advantages of Database Approach}
\vspace{11pt}

A database approach is more efficient and reliable than the file-based approach, as there is improved performance, data consistency, and easier maintenance.

There is also increased data independence, where applications are independent of data storage and data definitions. This leads to loose coupling, where applications and data are loosely coupled, making systems easier to modify and extend.

Additionally, with many DBMSs, there are high-level Database Languages provided, such as Structured Query Language (SQL), which is a standardized way to query and manipulate data. With SQL, users specify what they need, not how to retrieve it. SQL queries are executed by the DBMS, hiding low-level retrieval details, leading to transparent execution.

\vspace{11pt}
\textbf{Query Examples}
\vspace{11pt}

In a file-based Approach:

\vspace{11pt}
\begin{lstlisting}[language=SQL]
Procedure FindCustomer;
begin
    open file Customer.txt;
    Read(Customer)
    While not EOF(Customer)
        If Customer.name='Bart then
            display(Customer);
        EndIf
        Read(Customer);
    EndWhile;
End;
\end{lstlisting}
\vspace{11pt}

In a Database Approach (SQL):
\vspace{11pt}
\begin{lstlisting}[language=SQL]
SELECT *
FROM Customer
WHERE name = 'Bart'
\end{lstlisting}

\subsection{Elements of a Database System}
\vspace{11pt}

There are many elements of a Database System:
\begin{itemize}
    \item Database Model vs. Database Instances: Distinction between database structure and its current contents.
    \item Data Model: Concepts and rules used to describe data, relationships, and constraints.
    \item Three Layer Architecture: Separation of user views, logical structure, and physical storage.
    \item System Catalog: Metadata repository describing database structure and constraints.
    \item Database Users: Different user roles interacting with the database system.
    \item Database Languages: Languages used to define, query, and manipulate data.
\end{itemize}

\vspace{11pt}
\textbf{What is the Difference between a Database Schema and a Database State (Instance)?}
\vspace{11pt}

A Database Schema (or Model) describes the structure of the database, defines data items, data types, relationships, constraints, and storage details, is defined during database design and changes infrequently, and is stored in the DBMS catalog.

For example, in a Database Schema, it may have a structure such as:

Student(number, name, address, email)

Course (number, name)

Building (number, address)

\vspace{11pt}
Meanwhile, a Database State (Instance) represents the actual data stored in the database at a specific point in time. This is also called a database instance, and it changes frequently as data is inserted, updated, and deleted.

For example, database states (or instances) may be shown as tables with current tuples for STUDENT, COURSE, and BUILDING.

\vspace{11pt}
\begin{aside}
The schema remains relatively stable, while the database state changes over time as records are added, updated, or removed.
\end{aside}
\vspace{11pt}

\vspace{11pt}
\textbf{Data Model}
\vspace{11pt}

A database system uses multiple levels of data models - conceptual, logical, and physical, each describing the data from a different perspective. A well-designed data model is the foundation of a successful database application. A data model provides a clear and precise description of data items, relationships among data, and constraints on the data.

Types of Data Models include Conceptual data models, Logical data models, Internal (Physical) data models, and External data models.

\vspace{11pt}
\textbf{Conceptual Data Model}
\vspace{11pt}

A conceptual data model provides a high-level representation of data items, their characteristics, and relationships. It serves as a communication tool between information architects and business users. It is implementation-independent and focused on business concepts. It is also user-friendly and aligned with how business users view the data.

Conceptual data models are developed through close collaboration between information architects and business users. They are commonly represented using Enhanced Entity-Relationship (EER) models and Object-oriented models.

\vspace{11pt}
\textbf{Logical Data Model}
\vspace{11pt}

A logical data model refines the conceptual data model based on the chosen implementation environment. It maps conceptual concepts to a specific logical data framework, while remaining understandable to business users, while also closer to actual data structures.

A logical data model depends on the database paradigm used, such as Relational, Hierarchical, Object-oriented, Extended relational (object-relational), XML-based, and NoSQL. Logical data models serve as an intermediate step that can be mapped to the internal (physical) data model.

\vspace{11pt}
\textbf{Physical Data Model (Internal Data Models)}
\vspace{11pt}

A physical data model describes the physical storage details of the database. Specifically, it specifies where the data is stored, how the data is formatted on disk, and which indexes and access paths are used.

Physical data models focus on performance and storage efficiency. It is highly specific to the DBMS and underlying storage system.

\vspace{11pt}
\textbf{External Data Model}
\vspace{11pt}

An external data model consists of user-specific views, each representing a subset of the logical data model. A view shows only the data relevant to a particular application or user group (irrelevant data is hidden, simplifying data accesses).

Views are designed to meet the specific needs of applications or user groups. A single view may be used by one or more applications, while supporting access control and data security.

Some examples of views include a student registration application, which accesses a view with student data, while a capacity planning application accesses a view with building data.


\vspace{11pt}
\subsection{Three Layer Architecture for Database Model}
\vspace{11pt}

The three-layer architecture is a fundamental architecture for database systems and defines how different levels of data models interact with each other.

The architecture consists of three layers: External Layer (user-specific views), Conceptual (Logical) Layer (overall logical structure of the database, and the Internal Layer (physical storage details). Changes in one layer should have minimal impact on the other layers. This architecture creates modularity and improves efficiency, maintainability, performance, and security.

\vspace{11pt}
\textbf{Conceptual / Logical Layer}
\vspace{11pt}

Includes conceptual and logical data models. The logical/conceptual layer also describes data items, their characteristics, types, and relationships with each other. This layer is independent of physical DBMS implementation details.

\vspace{11pt}
\textbf{External Layer}
\vspace{11pt}

The external layer consists of external data models, or views, which provide controlled access to selected portions of the logical data model. Views are tailored to specific applications or user groups.

\vspace{11pt}
\textbf{Internal Layer}
\vspace{11pt}

The internal layer contains the internal (physical) data model. It defines how data is physically stored and organized, while also focusing on storage structures and access methods.

\vspace{11pt}
\textbf{Catalog (System Catalog \ Data Dictionary)}
\vspace{11pt}

The system catalog is a core component of a DBMS. The catalog stores metadata, or data definitions, about the database. Metadata contains definitions of views (external data models), logical data models, and internal (physical) data models. The system catalog ensures consistency and synchronization across different data models. The system catalog is used by the DBMS to manage, access, and validate data.

\vspace{11pt}
\textbf{Database Users}
\vspace{11pt}

There are many types of database users, each with unique roles.

The information architect designs the conceptual data model and works closely with business users to capture and model data requirements.

The database designer translated the conceptual model into logical and internal data models. They prepare the database design for implementations.

The database administrator (DBA) is responsible for database implementation and operation. They set up the database infrastructure, while continuously monitoring performance, including response time, throughput, and storage usage.

The application developer develops database applications using general-purpose programming languages. They implement application logic and interacts with the DBMS through APIs or embedded SQL.

Lastly, business users use the database applications to perform specific business tasks. They interact with the database indirectly through applications, not through the DBMS itself.

\vspace{11pt}
\textbf{Database Languages}
\vspace{11pt}

Every DBMS provides one or more database languages.

A Data Definition Language (DDL) is used to define database structures. It specifies external, logical, and internal data models, and is typically used by DBAs and application developers.

A Data Manipulation Language (DML) is used to retrieve, insert, delete, and modify data. It can be executed interactively or embedded in a programming language.

Meanwhile, Structured Query Language (SQL) provides a standard language for relational databases. It provides both DDL and DML capabilities.

\vspace{11pt}
\subsection{Advantages of Database Systems and Database Management}
\vspace{11pt}

\vspace{11pt}
\textbf{Data Independence}
\vspace{11pt}

Data independence is the ability to change data definitions with minimal impact on applications.

In physical data independence, applications, views, and the logical data model remain unchanged. Changes are made only to the internal (physical) data model. Examples include file organization, indexing, and storage location.

In logical data independence, applications are minimally affected by changes to the conceptual or logical data model. Changes at the conceptual/logical layer have little impact on external views.

\vspace{11pt}
\textbf{Database Modeling}
\vspace{11pt}

A data model explicitly represents data items, their characteristics, and relationships. A data model may also specify integrity rules and supported operations. Common types of data models include: Hierarchical models, (Enhanced) Entity-Relationship (EER) models, relational models, and object-oriented models.

A conceptual data model captures business data requirements. It is developed in collaboration with business users. The conceptual model is then translated into logical and internal data models. Clear documentation of assumptions and limitations is essential.

\vspace{11pt}
\textbf{Managing Diverse Data Types}
\vspace{11pt}

There are three general categories of data:
\begin{itemize}
    \item Structured Data: Well-defined schema and data types. Examples include student records (ID, name, address, email).
    \item Semi-Structured Data: Partial or flexible structure. Examples include JSON documents, resumes, and web data.
    \item Unstructured Data: No fixed schema. Examples include text documents, images, and videos.
\end{itemize}

Modern DBMSs can store, manage, and query all three types.

\vspace{11pt}
\textbf{Managing Data Redundancy}
\vspace{11pt}

\textbf{Controlled Data Redundancy} means that some data duplication may be intentional, especially in distributed systems, to improve performance.

\textbf{Consistency Management} means that the DBMS provides mechanisms to synchronize replicated data. This ensures data consistency across multiple copies.

\textbf{Automatic Data Correctness}, unlike file-based systems, means that the DBMS automatically enforces data consistency. No manual intervention by users or applications is required.

\vspace{11pt}
\textbf{Specifying Integrity Rules}
\vspace{11pt}

Data integrity rules ensure the correctness and validity of stored data. Meanwhile, syntactical rules define how data is represented and stored. Examples may include customerID that must be an integer, or birthdate that is stored as month, day, and year.

Semantic rules ensure the logical meaning of data. Examples may include customerID to be unique, Account balance must be greater than 0, and a customer cannot be deleted if pending invoices exist. Centralized enforcement means that integrity rules are part of the conceptual and logical data models and are stored in the catalog and enforced by the DBMS, not by applications.

\vspace{11pt}
\textbf{Concurrency Control}
\vspace{11pt}

DBMSs provide built-in support for concurrent and parallel database operations. Multiple users can simultaneously retrieve and update data. Read and write operations may be executed at the same time.

A key concept is a transaction. A transaction is a sequence of read/write operations treated as an atomic unit. Either all operations are executed, or none are. The DBMS ensures data consistency and prevents inconsistencies during concurrent access.

A DBMS must support ACID properties to ensure correct transaction processing.

\begin{itemize}
    \item Atomicity - A transaction is executed entirely or not at all.
    \item Consistency - A transaction moves the database from one valid state to another.
    \item Isolation - Concurrent transactions behave as if executed sequentially.
    \item Durability - Once committed, transaction results are permanently stored, even after failures.
\end{itemize}

\vspace{11pt}
\textbf{Backup and Recovery Facilities}
\vspace{11pt}

Backup and recovery facilities protect the database against data loss caused by hardware failures, network errors, and software bugs. Backup facilities support full backups and incremental backups. Recovery facilities restore the database to a previous consistent state.

\vspace{11pt}
\textbf{Data Security}
\vspace{11pt}

A DBMS enforces data security using access control mechanisms, where users are authenticated through logins and passwords.

Role-based Access Control (RBAC) assigns different permission levels to users. Examples include read-only access and read-write access. Authorization rules are defined per user or role and are stored in the catalog and enforced by the DBMS. An example includes the Vendor Managed Inventory (VMI) systems, which restrict access based on roles.

\vspace{11pt}
\textbf{Performance Utilities}
\vspace{11pt}

Key Performance Indicators (KPIs) include \textbf{response time }(time between issuing a request and receiving a result), \textbf{throughput} (number of transactions processed per unit time), and \textbf{space utilization} (storage used for raw data and metadata).

DBMS Performance Utilities optimize and distribute data storage, tune indexes for faster query execution, optimize queries to improve application performance, and improve buffer and memory management.

\subsection{Architecture of a DBMS - Design Principle \& Access Layer}
\vspace{11pt}

The design principle of a DBMS emphasizes separation of concerns between user interaction, query processing, and physical data management.

In the User Access Layer, users and applications interact with the DBMS through DDL statements (schema definitions), Interactive SQL queries, Application programs, and Database tools. All access is mediated by DBMS interfaces, providing data independence and a uniform access mechanism.

\vspace{11pt}
\subsubsection{Architecture of a DBMS: Core Component (Query Processor)}
\vspace{11pt}

The DBMS consists of two main subsystems. The first is the query processor which interprets and executes SQL statements. Its key components include DDL and DML compilers, query parser and a query rewriter, a query optimizer, and a query executor. Essentially, the query processor translates high-level SQL into efficient execution plans.

\vspace{11pt}
\subsubsection{Architecture of a DBMS: Core Component (Storage Manager and Database Storage)}
\vspace{11pt}

The second main subsystem of a DBMS is the storage manager and database storage. The storage manager manages physical data storage and access. Its key components include a transaction manager, buffer manager, lock manager, and recovery manager. The storage manager and database storage ensures concurrency control, efficient memory use, and system reliability. The Database Storage stores raw data, indexes, and system catalog (metadata).

\vspace{11pt}
\subsubsection{Connection and Security Managers}
\vspace{11pt}

The Connect Manager established a database connection (locally or through a network) and verifies logon credentials and provides a connection handle.

Meanwhile, the Security Manager ensures users have appropriate privileges. It manages access controls, including connection permissions and read vs. write access.

\vspace{11pt}
\subsubsection{DDL Compiler}
\vspace{11pt}

The DDL Compiler compiles the data definitions specified in \textbf{Data Definition Language (DDL)}. It performs the following steps:
\begin{itemize}
    \item Parsing: Checks the syntactical correctness of DDL statements.
    \item Translation: Converts data definitions into an internal format and generates errors if required.
    \item Registration: Upon successful compilation, store the data definitions in the database catalog.
\end{itemize}

\vspace{11pt}
\subsubsection{Query Processor Components}
\vspace{11pt}

The \textbf{Query Processor} is a critical component of a DBMS that handles query execution efficiently.

\begin{center}
    \includegraphics[width=0.5\textwidth]{6.jpg}
\end{center}

\vspace{11pt}
\textbf{DML Compiler}
\vspace{11pt}

The DML Compiler compiles \textbf{Data Manipulation Language (DML)} statements, including INSERT, UPDATE, DELETE, and SELECT. If the DML statement is a query, it collaborates with:
\begin{itemize}
    \item Query Parser: Analyzes the query's syntax and structure.
    \item Query Optimizer: Determines the most efficient execution plan.
    \item Query Executor: Runs the query and retrieves the results.
\end{itemize}

\vspace{11pt}
\textbf{Parser and Rewriter}
\vspace{11pt}

The Query Parser converts a query into an internal representation format. It validates the query for syntactical and semantical correctness using the database catalog. It also generates errors if the query is incorrect.

Meanwhile, the Query Rewriter simplifies the query using predefined rules and heuristics. It optimizes the query independently of the current database state. For example, in RDBMS, nested queries may be reformulated or flatted into join queries for better performance.

\vspace{11pt}
\textbf{Optimizer and Executor}
\vspace{11pt}

The Query Optimizer is a crucial component that enhances DBMS performance. It optimizes the query based upon the current database state (e.g., existing indexes). It generates multiple query execution plans and evaluates their cost in terms of number of I/O operations, CPU processing, and execution time. It combines catalog-based estimates with statistical inference to determine the most efficient execution plan.

The Query Executor executes the final execution plan generated by the optimizer. It interacts with the storage manager to retrieve the required data. It ensures the query is processed correctly and returns the desired results.

\vspace{11pt}
\subsection{Storage Manager}
\vspace{11pt}

The \textbf{Storage Manager} manages physical file access and ensures correct and efficient storage of data.

\begin{center}
    \includegraphics[width=0.5\textwidth]{7.jpg}
\end{center}

There are four main components of the Storage Manager:
\begin{itemize}
    \item Transaction Manager: Ensure ACID properties for database transactions.
    \item Buffer Manager: Handles cache memory for efficient data retrieval and minimizes disk I/O.
    \item Lock Manager: Manages concurrency control to prevent conflicts in multi-user environments.
    \item Recovery Manager: Ensures data integrity by handling failures and supporting rollback/recovery mechanisms.
\end{itemize}

\vspace{11pt}
\textbf{Transaction Manager}
\vspace{11pt}

The Transaction Manager supervises the execution of database transactions. \textit{A transaction is a sequence of read/write operations treated as a single unit}. It creates a schedule with interleaved read/write operations for efficient execution.

The transaction manager also ensures ACID properties: Atomicity (All operations complete or none do), Consistency (Preserves database integrity), Isolation (Prevents interference among concurrent transactions), and Durability (Committed results persist after failures). 

The Transaction Manager commits successful transactions and rolls back failed ones.

\vspace{11pt}
\textbf{Buffer Manager}
\vspace{11pt}

The Buffer Manager manages the buffer memory of the DBMS for efficient data retrieval. It caches data intelligently to reduce disk I/O operations. Additionally, it implements smart replacement strategies when the buffer is full. For example, the data locality principle is applied, where recently retrieved data is likely to be accessed again. The Buffer Manager also interacts with lock manager to handle concurrent access safely.

\vspace{11pt}
\textbf{Lock Manager}
\vspace{11pt}

The Lock Manager ensures concurrency control to maintain data integrity at all times. It manages assigning, releasing, and recoridng locks in the catalog. Two types of locks are supported based on data operation type:
\begin{itemize}
    \item Read Lock --- Allow multiple transactions to read simultaneously.
    \item Write Lock --- Ensure exclusive access for modifying data.
\end{itemize}

The Lock Manager uses a locking protocol to define locking rules. It also maintains a lock table to track lock information.

\vspace{11pt}
\textbf{Recovery Manager}
\vspace{11pt}

The Recovery Manager ensures the correct execution of database transactions and maintains database integrity. It maintains a log file to keep track of all database operations. It supports transaction rollback by undoing actions of aborted transactions. Additionally, the Recovery Manager performs crash recovery, ensuring data consistency after system failures.

\vspace{11pt}
\subsubsection{DBMS Utilities}
\vspace{11pt}

Database utility tools improve performance and simplify database maintenance. A \textbf{Loading Utility} facilitates data loading from various sources, including other DBMS systems, text files, Excel files, and other structured/unstructured data formats.

A \textbf{Reorganization Utility} automatically optimizes data storage for better performance. It enhances query efficiency by restricting data organization.

\textbf{Performance Monitoring Utilities} track key performance indicators to monitor DBMS performances, including storage space consumption, query response times, and transactions throughput rates.

\textbf{User Management Utilities} facilitate user and group account management. It supports the assignment of privileges and access control to ensure security.

\textbf{Backup and Recovery Utilities} provide database backup and recovery mechanisms to protect against data loss. It ensures data consistency after system failures or unexpected crashes.

    \item Web-based interface
    \item Admin interface
    \item Stand-alone query language interface
    \item Forms-based interface
    \item Natural Langage interface
    \item Network Interface
\end{itemize}

\subsection{Categorization of DBMSs}
\vspace{11pt}

DBMSs can be classified along multiple, largely independent dimensions, reflecting differences in data representation, system architecture, workload, and usage patterns.

\vspace{11pt}
\subsubsection{Categorization by Data Model}
\vspace{11pt}

From a Conceptual/Logical Level:
\begin{itemize}
    \item Hierarchical DBMSs
    \item Network DBMSs

\subsubsection{Categorization Based on Usage Workload}
\vspace{11pt}

From a Query and access pattern perspective:
\begin{itemize}
    \item Transaction databases (OLTP)
    \item Analytical databases (OLAP)
    \item Hybrid Transaction/Analytical Processing (HTAP)
\end{itemize}

\vspace{11pt}
\textbf{Transaction Databases}
\vspace{11pt}

\textbf{Online Transaction Processing (OLTP)} Databases focus on managing operational or transactional data. The database server must process a high volume of simple transactions efficiently. The DBMS must have fast response time for short, frequent queries.

\vspace{11pt}
\textbf{Analytical Databases}
\vspace{11pt}

\textbf{Online Analytical processing (OLAP)} Databases use operational data for tactical or strategical decision-making. A limited number of users execute complex queries for business intelligence. The DBMS must efficiently handle complex queries, often in lower frequency.

\vspace{11pt}
\textbf{Hybrid Transaction/Analytical Processing}
\vspace{11pt}

\textbf{Hybrid Transaction/Analytical Processing (HTAP)} systems are designed to support both transactional (OLTP) and analytical (OLAP) workloads on the same database, in near real time.

Key characteristics include a unified data platform for transactions and analytics. HTAPs also eliminates data movement between OLTP and OLAP systems, and it supports real-time or near-real-time analytical queries.

The Benefits of HTAPs include fresh analytics on operational data, simplified system architecture, and reduced data latency and redundancy. Meanwhile, the challenges of HTAPs include balancing performance isolation between OLTP and OLAP and complex concurrency control and query optimization.

\vspace{11pt}
\begin{aside}
    HTAP is increasingly important in modern cloud and in-memory database systems.
\end{aside}

\vspace{11pt}
\subsubsection{DBMSs Span Multiple Dimensions}
\vspace{11pt}

Modern DBMSs cannot be classified using a single criterion.

Example 1: A modern cloud-based NoSQL DBMS may simultaneously be: Non-relational in its data model, distributed in architecture, multi-user, and designed for OLTP or HTAP workloads.

Example 2: NewSQL DBMS is a relational data model, distributed architecture, multi-user, and OLTP-oriented.

The takeaway is that no single taxonomy fully captures modern DBMSs. Real-world systems occupy multiple points in the design space.

The most recent major version is UML 2.5, released in 2017.

UML includes multiple diagram types: Use cases, sequence, package, deployment, and others. From a database modeling perspective, the class diagram is the most relevant.

\textbf{UML class diagrams} are widely used to represent ER-style concepts --- such as entities, attributes, and relationships in many commercial database design tools.

\textbf{Recap of Object Orientation}
\vspace{11pt}

A class is a blueprint that defines a set of objects (comparable to an entity type in the ER model). An object is an instance of a class (Comparable to an entity in the ER model). An object is characterized by Variables (attributes) and Methods (operations.

Variables correspond to attribute types, and variable values correspond to attributes in ER. Methods have no direct equivalent in ER models.

For example, there is a Student class. Objects include Bart, Wilfried, and Seppe. Variables include name, gender, and birthdate. Methods include calcAge(), isBirthday(), and hasPassed(courseID).

\textbf{Information Hiding (Encapsulation)} is where object variables are accessed only through getter and setter methods. A \textit{getter} retrieve the value of the variable while a \textit{setter} assigns or updates the value of a variable.

\textbf{Inheritance} is where a superclass can have one or more subclasses. Subclasses inherit both variables and methods from the superclass.

\textbf{Method Overloading} is where multiple methods in the same class may share the same name. Methods are distinguished by different numbers or types of input parameters (method signature).

\subsection{Classes, Variables, and Access Modifiers}
\vspace{11pt}

\textbf{Classes in UML}
\vspace{11pt}

In a UML class diagram, a class is represented as a rectangle with three sections. The Top is the class name, the middle are variables (attributes), and the bottom are methods (operations).

\textbf{Variables in UML}
\vspace{11pt}

UML provides primitive data types such as String, Integer, and Boolean. UML also allows user-defined data types (domains).

UML also supports \textbf{Composite variables} and\textbf{ Multi-valued variables}. Composite variables may decompose into components (e.g., first name, last name) or they define and reuse a custom domain (e.g., Name\_Domain). Multi-valued variables use multiplicity to indicate how many values a variable may have for one object. (e.g., email: String [0.. 4], email: String [*] (unbounded)).

\textbf{Derived Variables} are indicated by a leading forward slash (e.g., /age).

\textbf{Variables with Unique Values}: UML does not explicitly model key attributes as in ER. UML assumes an object-oriented DBMS (OODBMS) implementation. 

Each object is assigned a unique, \textbf{Immutable Object Identifier (OID)}. The OID uniquely identifies objects throughout their lifetime. Therefore, no separate key variables are required in UML.

\textbf{Access Modifiers}
\vspace{11pt}

Access modifiers specify who can access a class's variables or methods. There are three primary access levels:
\begin{itemize}
    \item Private (denoted by '-'): Accessible only within the class.
    \item Public (denoted by '+'): Accessible by any other class.
    \item Protected (denoted by '\#'): Accessible by the class and subclasses.
\end{itemize}

As a general design guideline, it is important to declare all variables as private to support information hiding.

\textbf{Unidirectional vs. Bidirectional Association}
\vspace{11pt}

Associations may include navigation arrows to indicate direction. The arrow specifies the allowed direction of access or querying.

In a Unidirectional Association, navigation is possible in one directly own and is shown using a single arrow. Meanwhile, in a Bidirectional Association, navigation is possible in both directions and no arrow is shown.

For example, all purchase orders can be retrieved from a supplier object. It is not possible to navigate from a purchase order to its supplier.

\textbf{Qualified Association}
\vspace{11pt}

A qualified association is a special type of binary association. It uses a qualifier to further restrict or refine the association. The qualifier consists of one or more key variables that index a subset of related objects. The qualifier acts like a key, selecting a specific related object and thereby reducing the effective multiplicity. A qualifier is shown as a small rectangle attached to the association end.

\vspace{11pt}
\begin{center}
    \includegraphics[width=.65\textwidth]{18.png}
\end{center}

In a navigation context, a qualifier is used to select a specific related object from all objects participating in the association. In an implementation context, each qualifier value references a unique target object. When an application requires data retrieval based on search keys, qualified associations are generally appropriate.

For example, in the diagram above, the association \texttt{PLAYS AT} Connects \texttt{Team} and \texttt{Player}. The association is qualified by the attribute \texttt{position}. This qualifier acts a an index or key: Given a team and a position, at most one player is identified.

As a result, the effective multiplicity on the player side is \texttt{0..1}. The small rectangle labeled position visually represents the qualifier.

\vspace{11pt}
\textbf{Qualified Association: ER vs. UML Example}
\vspace{11pt}

ER Model: There exists a 1:N relationship between TEAM and PLAYER. A team can have zero to many players. A player is always related to exactly one team.

UML (Qualified Association): The association is qualified by position. For a given team and position, there are zero or one players. A player still belongs to exactly one team.

\textbf{Aggregation}

\textbf{Object Constraint Language (OCL)}
\vspace{11pt}

Object Constraint Language (OCL) is used to specify constraints in UML models. OCL constraints are declarative, meaning they specify what must be true rather than how it is enforced. Additionally, OCL contains no control flow or procedural code.

Typical uses of OCL include
\begin{itemize}
    \item Class invariants
    \item Preconditions and postconditions for methods
    \item Navigation across associations
    \item Constraints on operations and attributes
\end{itemize}
\vspace{11pt}

OCL is standardized by the Object Management Group (OMG)

\vspace{11pt}
\textbf{OCL: Class Invariant and Pre/Post Conditions}
\vspace{11pt}

Class Invariant --- a class invariant is a constraint that must hold for \textbf{all objects} of a class. For example, SUPPLIER: SUPSTATUS > 100 (The status of every supplier must be greater than 100).

Preconditions and Postconditions --- Preconditions must be true before a method is executed, while postconditions must be true after the method completes. For example, (Pre) before withdrawal, the balance must be positive. For Post, after withdrawal, the balance must still be positive.

\textbf{Association vs. Dependency (Conceptual Difference)}
\vspace{11pt}

Dependency --- Represents a temporary "uses" relationship between classes. One object uses another within a method. No stored reference is maintained. A dependency only exists during method execution. Dependencies are shown as a dashed arrow in UML. An example is an Employee temporarily using a Course object.

\topsec{Lecture 4 --- Extended Relational Databases (Object-Relational Databases)}

\subsec{Success of the Relational Model}

The relational model is highly effective for managing well-structured numerical and alphanumerical data. It has a strong mathematical foundation and simplicity.

There are two core concepts related to it:
\begin{itemize}
    \item Tuple: A tuple represents a set of attribute values describing one entity instance.
    \item Relation: A relation is a mathematical set of tuples describing similar entities.
\end{itemize}
\vspace{11pt}

\textbf{Value Based Model}: Relationships are defined using data values. ($\leftrightarrow$ identity based OO model).

The relational model also used a descriptive, non-navigational query language (SQL).

\subsec{Limitations of the Relational Model}

The relational model requires data to be fully normalized. Information about a single entity may be fragmented across multiple relations.

Relations are connected only through primary-foreign key values. Additionally, Value-based relationships lead to frequent and expensive joins.

There is also limited support for specialization, categorization, and aggregation (These concepts require additional tables and complex queries).

\vspace{11pt}
Other limitations include:
\begin{itemize}
    \item Relations stores only atomic values.
    \item Composite and multi-valued attributes cannot be directly represented.
    \item \textbf{No direct support of modeling behavior or methods}.
    \item Limited support for stored functions to reduce network traffic and code duplication (Applications often retrieve large amounts of raw data and perform filtering, aggregation, or computation on the client side $\to$ More round trips between application and the DB).
    \item \textbf{Difficult to represent complex objects} (e.g., multimedia, spatial data, genomics, time series and IOT data).
    \item Weak support for unstructured or semi-structured data (audio, video, text).
\end{itemize}
\vspace{11pt}

\subsec{Object-Relational DBMS}

\boldsecbottom{DBMS and OO Paradigm}

The object-oriented (OO) paradigm originated in languages such as C++ and Smalltalk. Additionally, \textbf{Object-Oriented DBMSs (OODBMS)} evolved from OO programming languages.

Database features were later added, including querying, concurrency control, and transaction management.

OODBMSs \textbf{stores persistent objects directly}, without mapping to relational tables. OODBMSs also supported \textbf{ACID properties}. However, OODBMSs are complex and lack a widely accepted standard query language such as SQL.

\boldsec{Object-Relational RDBMS Extensions}

\textbf{Object-Relational DBMSs (ORDBMSs)} retain \textbf{relations as the fundamental building structure}. SQL also remains the core language for DDL and DML.

The relational model is \textbf{extended with object-oriented features}:
\begin{itemize}
    \item User-Defined Types (UDTs)
    \item User-Defined Functions (UDFs)
    \item Inheritance
    \item Encapsulated behavior (methods)
    \item Polymorphism
\end{itemize}
\vspace{11pt}

\begin{aside}
    Note on Extended SQL Syntax: Extended SQL syntax may vary across different ORDBMSs. However, the core object-relational concepts are largely consistent. For Oracle-specific syntax and features, refer to the Oracle Object-Relational Developer's Guide (\href{https://docs.oracle.com/en/database/oracle/oracle-database/26/adobj/index.html}{Oracle OR Guide}).
\end{aside}

\sssec{User-Defined Types (UDTs)}

The Standard SQL data types include \texttt{CHAR}, \texttt{VARCHAR}, \texttt{INT}, \texttt{FLOAT}, \texttt{DOUBLE}, \texttt{DATE}, \texttt{TIME}, etc.

These built-in types are insufficient for modeling complex real-world objects. Therefore, \textbf{User-Defined Types (UDTs)} allows users to define customized data types with specific structure and properties, enabling richer data modeling in ORDBMSs.

\boldsec{UDTs}

The General Syntax:

\vspace{11pt}
\texttt{CREATE TYPE <typename> AS ( <list of attributes, similar to CREATE TABLE> );}
\vspace{11pt}

For example:

\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TYPE BarType AS (
    name CHAR(20),
    addr CHAR(20)
);
\end{lstlisting}
\vspace{11pt}

Oracle Specific Syntax: Oracle requires the keyword \texttt{OBJECT}.

\vspace{11pt}
\texttt{CREATE TYPE <typename> AS OBJECT ( <list of attributes, similar to CREATE TABLE> );}
\vspace{11pt}

\boldsecbottom{Constructor, Generator, and Mutator}

Each UDT has a type constructor with the same name as the type. The constructor creates (wraps) an object of that UDT. In SQL-1999, each attribute of a UDT has:
\begin{itemize}
    \item A Generator method (to retrieve the attribute).
    \item a Mutator method (to modify the attribute value).
\end{itemize}
\vspace{11pt}

For an attribute A:
\begin{itemize}
    \item \texttt{Generator: A()}.
    \item \texttt{Mutator: A(v) where v is the new value}.
\end{itemize}
\vspace{11pt}

\boldsecbottom{UDT Usage as Table Type}

Define a UDT

\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TYPE BarType AS OBJECT (
    name CHAR(20),
    addr CHAR(20)
);
\end{lstlisting}
\vspace{11pt}

Create a table of the UDT: \texttt{CREATE TABLE Bars OF BarType;}

Insert a row using the constructor: \texttt{INSERT INTO Bars VALUES( BarType('Joe''s Bar', 'Maple St.'));}

Query attributes using generators: 

\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
SELECT b.name, b.addr
FROM bars b
\end{lstlisting}
\vspace{11pt}

\boldsecbottom{UDT Usage as Column Type}

Define a UDT:
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TYPE BeerType AS OBJECT (
    name CHAR(20),
    manf CHAR(20)
);
\end{lstlisting}
\vspace{11pt}

Use the UDT as a column type:
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TABLE Drinks (
    name CHAR(30),
    addr CHAR(50),
    favBeer BeerType
);
\end{lstlisting}
\vspace{11pt}

Inserting data using the constructor: \texttt{INSERT INTO Drinkers VALUES ('Smith', '2101 Coliseum Blvd, Chicago, 4444', BeerType('Miler', 'OBBBB'));}

\boldsec{Different Types of UDTs}

\begin{itemize}
    \item \textbf{Distinct Data Types}: Extend existing SQL data types.
    \item \textbf{Opaque Data Types}: Define completely new data types with hidden internal structure.
    \item \textbf{Unnamed row types}: Use unnamed tuples as attribute values.
    \item \textbf{Named row types}: Named row types: Use named tuples as attribute values.
    \item \textbf{Table data types}: define tables as instances of table types.
\end{itemize}
\vspace{11pt}

\begin{aside}
    NOTE: Not all ORDMBS products support every type of UDT. Always verify which UDT features are supported by a specific ORDBMS.
\end{aside}

\vspace{11pt}
\boldsec{UDT --- Distinct Data Type}

A distinct data type is a user-defined data type derived from an existing SQL base type. It shares the same underlying representation but represents a \textbf{semantically different domain}.\textbf{ Distinct types improve type safety and semantic clarity}.

\vspace{11pt}
Define distinct data types:

\texttt{CREATE DISTINCT TYPE us-dollar AS DECIMAL(8,2)}

\texttt{CREATE DISTINCT TYPE euro AS DECIMAL(8,2)}

\vspace{11pt}
Use distinct data types
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TABLE account(
    accountno SMALLINT PRIMARY KEY NOT NULL,
    amount-in-dollar us-dollar,
    amount-in-euro euro
);
\end{lstlisting}
\vspace{11pt}

Distinct data types enforce strong typing. The value of a distinct type cannot be directly compared with base type values.

For example:
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
SELECT *
FROM account
WHERE amount-in-euro > 1000 # Error! Type incompatibility

SELECT *
FROM account
WHERE amount-in-euro > euro(1000) # Corret usage with explicit cast
\end{lstlisting}
\vspace{11pt}

ORDBMSs may automatically support casting between a distinct type and it base type when explicitly requested.

\boldsec{UDT --- Opaque Data Type}

An \textbf{opaque data type} is a completely new user-defined data type. It is not based on any existing SQL base type. The internal structure is hidden from users and the DBMS. 

These types are commonly used for complex or non-traditional data (e.g., image, audio, video, fingerprints, text, spatial data, RFID tags, QR codes, etc.).

\vspace{11pt}
Defining Opaque Data Types:

\texttt{CREATE OPAQUE TYPE image AS <\dots>}

\texttt{CREATE OPAQUE TYPE fingerprint AS <\dots>}

Using an opaque data type:
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TABLE employee
(
    ssn SMALLINT NOT NULL,
    name CHAR(25) NOT NULL,
    ...
    empFingerprint fingerprint,
    photogrph image
);
\end{lstlisting}
\vspace{11pt}

\boldsec{UDT --- Unnamed Row Type}

An \textbf{unnamed row type} represents a composite value using the \texttt{ROW} keyword. The row structure is defined inline and has no explicit type name. Attributes can be built-in types, distinct types, or opaque types.

\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TABLE employee
(
    ssn SMALLINT NOT NULL,
    name ROW(fname CHAR(25), lname CHAR(25)),
    address ROW(streetAddress CHAR(20) NOT NULL, zipCode CHAR(8), city CHAR(15) NOT NULL),
    empFingerprint fingerprint,
    photograph image
);
\end{lstlisting}
\vspace{11pt}

\boldsec{UDT --- Named Row Type}

A \textbf{named row type} is a user-defined data type. It groups coherent set of attributes into a single structure. The composite structure is assigned a meaningful type name.

The type can be reused in:
\begin{itemize}
    \item Table definitions
    \item Queries
    \item Any context where a standard SQL data type is allowed
\end{itemize}
\vspace{11pt}

An Example of a Named Row Type (General Syntax)
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE ROW TYPE address AS (
    streetAddress CHAR(20),
    zipCode CHAR(8),
    city CHAR(15) NOT NULL
);

CREATE TABLE employee (
    ssn SMALLINT NOT NULL,
    fname CHAR(25) NOT NULL,
    lname CHAR(25) NOT NULL,
    empAddress address
    ...
    empFingerprint fingerprint
    photograph image
);
\end{lstlisting}
\vspace{11pt}

Oracle Specific Syntax
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TYPE address AS OBJECT (
    streetAddress CHAR(20),
    zipCode CHAR(8),
    city CHAR(15) NOT NULL
);

CREATE TABLE employee (
    ssn SMALLINT NOT NULL,
    fname CHAR(25) NOT NULL,
    lname CHAR(25) NOT NULL,
    empAddress address
    ...
    empFingerprint fingerprint
    photograph image
);
\end{lstlisting}
\vspace{11pt}

More examples of Named Row Type

General Syntax:

\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
SELECT lname, empaddress
FROM employee
WHERE empaddress.city = 'LEUVEN'
\end{lstlisting}
\vspace{11pt}

\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]

WHERE E1.empaddress.city = 'LEUVEN'

SELECT E1.lname, E1.empaddress

\end{lstlisting}
\vspace{11pt}

\boldsec{UDT --- Table Data Type}

A \textbf{table data type}, called a typed table, defines the type of a table. Similar to a class in object-oriented programming, each row in the table is an object of the specified type.

Defining a table type:
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TYPE employeetype AS OBJECT
(
ssn SMALLINT,
fname CHAR(25),
lname CHAR(25),
empAddress address
empFingerprint fingerprint,
photograph image
);
\end{lstlisting}
\vspace{11pt}

Creating a typed table: \texttt{CREATE TABLE employee OF TYPE employeetype}

Example Usage of Table Data Type (General Syntax):
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TABLE employee of TYPE employeetype
PRIMARY KEY (ssn);

CREATE TABLE ex-employee OF TYPE employeetype
PRIMARY KEY (ssn);
\end{lstlisting}
\vspace{11pt}

Oracle-Specific Syntax
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TABLE employee OF employeetype
(ssn PRIMARY KEY);

CREATE TABLE ex-employee OF employeetype
(ssn PRIMARY KEY);
\end{lstlisting}
\vspace{11pt}

\boldsec{Object Identifiers Using Reference Types}

If $T$ is a type, then \textbf{REF} $T$ denotes a\textbf{ reference to an object of type $T$}. A reference acts like a pointer to an object. Reference provide object identity in ORDBMSs. They correspond to OIDs in Object-Oriented DBMSs.

Unlike OIDs, however, references can be explicitly declared, queried, and displayed.

For example:
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TYPE MenuType AS (
    bar REF BarType,
    beer REF BeerType,
    price float
);
\end{lstlisting}
\vspace{11pt}

\img[0.5]{27.png}

Example (General Syntax)
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TYPE departmenttype (
    dnr smallint not null,
    dname char(25) not null,
    dlocation address,
    manager REF(employeetype)
);
\end{lstlisting}
\vspace{11pt}

Oracle Specific Syntax
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TYPE departmenttype (
    dnr smallint not null,

\end{aside}
\vspace{11pt}

\boldsec{Following REF}

A reference (REF) can be de referenced to access the object it points to. The \texttt{DEREF()} function retrieves the actual object from a reference.

Oracle Example:
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
SELECT DEREF(ss.beer).name, DEREF(ss.beer).manufacture

WHERE DEREF(ss.bar).name = 'Joe''s Bar';
\end{lstlisting}
\vspace{11pt}

Equivalent query using dot notation:
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
SELECT ss.beer.name, ss.beer.manufacture
FROM Sells ss
WHERE ss.bar.name = 'Joe''s Bar';
\end{lstlisting}
\vspace{11pt}

\textbf{In Oracle, dot notation can be used as a shorthand for dereferncing}.

\boldsec{REF and DEREF Examples with ORACLE}
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TYPE address_obj AS OBJECT

\sssec{User-Defined Functions (UDFs)}

RDBMSs provide many built-in functions (e.g., \texttt{MIN()}, \texttt{MAX()}, \texttt{AVG()}).

\textbf{User-defined functions (UDFs)} allow users to define their own functions. UDFs extend the functionality of SQL. Each UDF consists of:
\begin{itemize}
    \item a function name.
    \item input and output parameters.
    \item An implementation.
\end{itemize}
\vspace{11pt}

UDFs are stored and executed inside the ORDBMS. Additionally, UDF implementations are hidden from application programs.

UDFs can be overloaded (same name, different parameters) and there are two main types of UDF implementations:
\begin{itemize}
    \item Sourced functions
    \item External functions
\end{itemize}
\vspace{11pt}

\newpage
\boldsecbottom{UDF with Sourced Function}

\textbf{A sourced-function} is a UDF that is based on an existing built-in function. It adapts a built-in function to work with a user-defined type. Source functions reuse existing DBMS functionality while preserving strong typing.
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE DISTINCT TYPE MONETARY AS DECIMAL (8,2);
CREATE FUNCTION avg(monetary)
RETURNS MONETARY
SOURCE AVG(DECIMAL(8,2)) -- Indicates that this function is based on the existing built-in AVG function for the DECIMAL(8,2) type.

SELECT dnr, avg(salary)
FROM employee
GROUP by dnr;
\end{lstlisting}
\vspace{11pt}

\boldsecbottom{UDF with External Function}

\textbf{External functions} are UDFs implemented in an external host language. Common host languages include C/C++, Java, and Python.

Unlike sourced functions, external functions do not rely on existing SQL built-in functions. External functions can return:
\begin{itemize}
    \item A single value (scalar function).
    \item A set or table of values (table function).
\end{itemize}
\vspace{11pt}

\boldsecbottom{Interface of UDFs}

ORDBMSs can associate function interfaces (signatures) with data types and tables. Only the interface is exposed, but the implementation remains hidden. This separates what a function does from how it is implemented.

This supports information hiding and encapsulation. Functions can also be declared as part of a type definition:
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TYPE type-name (
    <list of component attributes and their types>
    <function (methods) declarations>
);
\end{lstlisting}
\vspace{11pt}

Example --- Interface of UDF

Define a type with a method interface

\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TYPE employeetype
( ssn SMALLINT NOT NULL,
fname CHAR(25) NOT NULL,
lname CHAR(25) NOT NULL,
empAddress INTERNATIONAL_ADDRESS,
...
empfingerprint FINGERPRINT,
photograph IMAGE,
FUNCTION age(employeetype) RETURNS integer
);
\end{lstlisting}
\vspace{11pt}

Create a typed table: \texttt{CREATE TABLE employee OF TYPE employeetype PRIMARY KEY (SSN);}

Use the method in a query

\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
SELECT ssn, fname, lname, photograph
FROM employee
WHERE age = 60
\end{lstlisting}
\vspace{11pt}

\boldsecbottom{UDF Example with Oracle}
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TYPE demo_type2 AS OBJECT (
    a1 NUMBER,
    MEMBER FUNCTION get_square RETURN NUMBER
);

-- Define the method implementation
CREATE TYPE BODY demo_type2 IS
    MEMBER FUNCTION get_square RETURN NUMBER IS
    x NUMBER;
    BEGIN
        SELECT c.col.a1*c.col.a1
        INTO X
        FROM demo_tab2 c;
        return (x);
    END;
END;
\end{lstlisting}
\vspace{11pt}

\begin{aside}
    Oracle clearly separates the method interface from the method implementation, supporting encapsulation.
\end{aside}
\vspace{11pt}

Example Use:

\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TABLE demo_tab2 (
    col demo_type2
);

INSERT INTO demo_tab2 VALUES(demo_type2(2));

SELECT t.col.get_square()
FROM demo_tab2 t; 
-- output: 4
\end{lstlisting}

\sssec{Inheritance}

Object-Relational DBMSs extend relational DBMSs with explicit support for inheritance. Inheritance is supported at
\begin{itemize}
    \item the data type level.
    \item the typed table level.
\end{itemize}
\vspace{11pt}

\boldsec{Inheritance at the Data Type Level}

A \textbf{child data type} inherits all attributes of its parent data type. The child type can \textbf{specialize} the parent by adding new attributes.

\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE ROW TYPE address AS (
    streetAddress CHAR(20) NOT NULL,
    zipCode CHAR(8),
    city CHAR(15) NOT NULL
);

CREATE ROW TYPE international_address AS (
    country CHAR(25) NOT NULL
) UNDER address;
\end{lstlisting}
\vspace{11pt}

\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TABLE employee ( 
    ssn SMALLINT NOT NULL,
    fname CHAR(25) NOT NULL,
    lname CHAR(25) NOT NULL,
    empAddress international_address,
    salary monetary,
    ...
    empfingerprint fingerprint,
    photograph image
);

SELECT fname, lname, empaddress
FROM employee
WHERE empaddress.country = 'USA' AND empaddress.city LIKE 'Fort%'
\end{lstlisting}
\vspace{11pt}

\boldsec{Inheritance at the Table Type Level}

Inheritance can also be applied at the \textbf{table (type) level}. A subtype table inherits all attributes of its parent table type. The subtype can add its own specialized attributes.

\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TABLE employee ( 
    ssn SMALLINT NOT NULL,
    fname CHAR(25) NOT NULL,
    lname CHAR(25) NOT NULL,
    empAddress international_address,
    salary monetary,
    ...
    empfingerprint fingerprint,
    photograph image
);

CREATE TYPE engineertype AS (
    degree CHAR(10) NOT NULL,
    license CHAR(20) NOT NULL
) UNDER employeetype;

CREATE TYPE managertype AS (
    startdate DATE,
    title CHAR(20))
) UNDER employeetype;

-- Create tables using various table types.
CREATE TABLE employee OF TYPE employeetype
PRIMARY KEY (SSN);

-- these new tables inherit the table structure, primary key, and participation in polymorphic queries.
CREATE TABLE engineer of TYPE engineertype UNDER employee;
CREATE TABLE manager OF TYPE managertype UNDER employee;
\end{lstlisting}
\vspace{11pt}

Query Examples

\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
SELECT ssn, fname, lname, startdate, title
FROM manager;

SELECT ssn, fname, lname
FROM employee; -- Tuples added to a sub table are automatically visible to queries on the super table. This query retrieves all employees, including the managers and engineers.

SELECT ssn, fname, lname
FROM ONLY employee -- Include only rows of Employee (exclude the sub tables)
\end{lstlisting}
\vspace{11pt}

\boldsec{Inheritance Example with Oracle}

\img[0.7]{28.png}

\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]

    name VARCHAR(100), 
    ssn NUMBER
) NOT FINAL;

CREATE TYPE employee_t UNDER person_t (
    department_id NUMBER,

\end{lstlisting}

\sssec{Polymorphism, Overloading, and Overriding}

\boldsec{Polymorphism}

A \textbf{subtype} inherits all attributes and functions of its \textbf{supertype}. A subtype may \textbf{override} inherited functions with specialized implementations. 

\textbf{Polymorphism}: The same function call can invoke different implementations depending on the object's type. The \textbf{same function name} can have \textbf{different implementations} of different subtypes. The DBMS selected the appropriate implementations \textbf{based on the object's actual type}.

This is similar to method overriding and dynamic dispatch in object-oriented programming.

\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE FUNCTION total_salary(e EMPLOYEE)
RETURN INTEGER
AS RETURN e.salary;

-- This query will retrieve the TOTAL_SALARY of managers.
CREATE FUNCTION total_salary(m Manager)
RETURN INTEGER
AS RETURN m.salary + m.monthly_bonus

-- This query will retrieve the TOTAL_SALARY of all employees, both managers and non-managers (a manager is an employee).
SELECT total_salary(e) FROM EMPLOYEE e
\end{lstlisting}
\vspace{11pt}

\boldsec{Overloading}

\textbf{Overloading} functions(or subprograms) allows multiple subprograms to share the same name. The subprogram must differ in:
\begin{itemize}
    \item Number of parameters, or
    \item Parameter order, or
    \item Parameter data type
\end{itemize}
\vspace{11pt}

\textbf{Overloading is a form of compile-time polymorphism}.

Example [Oracle Syntax]: Define the inherited method \texttt{Enlarge()} to detail with different types of input parameters.

\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TYPE Shape_typ AS OBJECT (
    ...
    MEMBER PROCEDURE enLarge (x NUMBER),
    ...
) NOT FINALl

CREATE TYPE Circle_typ UNDER Shape_type (
    ...
    MEMBER PROCEDURE Enlarge(x CHAR(1))
);

-- Oracle Example: Overloading
DECLARE 
    TYPE DateTabTyp IS TABLE OF DATE INDEX BY PLS_INTEGER; -- PLS_INTEGER type is a type for storing signed integers
    TYPE NumTabTyp IS TABLE OF NUMBER INDEX BY PLS_INTEGER; 
    hiredate_tab DateTabTyp; 
    sal_tab NumTabTyp; 
    PROCEDURE initialize (tab OUT DateTabTyp, n INTEGER) IS 
        BEGIN 
            FOR i IN 1..n LOOP 
            tab(i) := SYSDATE; 
        END LOOP; 
    END initialize; 
    PROCEDURE initialize (tab OUT NumTabTyp, n INTEGER) IS 
    BEGIN 
        FOR i IN 1..n LOOP 
            tab(i) := 0.0; 
        END LOOP; 
    END initialize; 
BEGIN 
    initialize(hiredate_tab, 50); -- calls first (DateTabTyp) version 
    initialize(sal_tab, 100); -- calls second (NumTabTyp) version 
END; /
\end{lstlisting}
\vspace{11pt}

\boldsec{Overriding}

\textbf{Overriding} means defining two methods with the \textbf{same name and the same parameter list}. One method is defined in the \textbf{parent data type} and the other method is defined in the \textbf{child data types}. The child method provides a \textbf{specialized implementation}.

Method selection is based on the runtime type of the object.
\vspace{11pt}

Example [Oracle]: Redefine an inherited method Area() to make it do something different
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TYPE Shape_typ AS OBJECT (
    ...,
    MEMBER PROCEDURE Area(),
    FINAL MEMBER FUNCTION id(x NUMBER),
    ...
);

-- Circle_typ specializes Shape_typ
CREATE TYPE Circle_typ UNDER Shape_typ (
    ...,
    OVERRIDING MEMBER PROCEDURE Area(),
    ...
);

-- Oracle Example Overriding
CREATE TYPE super_t AS OBJECT (
    n NUMBER, 
    MEMBER FUNCTION func RETURN NUMBER
) NOT final;

CREATE TYPE BODY super_t AS 
    MEMBER FUNCTION func RETURN NUMBER IS 
    BEGIN RETURN 1; END; 
END;

CREATE OR REPLACE TYPE sub_t UNDER super_t (
    n2 NUMBER, 
    OVERRIDING MEMBER FUNCTION func RETURN NUMBER
) NOT final; 

CREATE TYPE BODY sub_t AS 
    OVERRIDING MEMBER FUNCTION func RETURN NUMBER IS 
    BEGIN RETURN 2; END; 
END;

CREATE OR REPLACE TYPE final_t UNDER sub_t (
    n3 NUMBER
);

DECLARE 
    v super_t := final_t(100); -- v is an instance of super_t, but a value of sub_t to it. So,
BEGIN
    DBMS_OUTPUT.PUT_LINE(v.func); -- prints 2 (since v inherits sub_t func method)
END;
\end{lstlisting}
\vspace{11pt}

\sssec{Collection Types}

\boldsec{Collection Types}

Collection types allow attributes to store \textbf{multiple values}. Collections may contain
\begin{itemize}
    \item Standard SQL data types, or
    \item User-defined types (UDTs)
\end{itemize}
\vspace{11pt}

Common collection types include
\begin{itemize}
    \item \textbf{Set}: unordered collection, no duplicate elements.
    \item \textbf{Multiset (Bag)}: unordered collection, duplicates allowed.
    \item \textbf{List}: ordered collection, duplicates allowed
    \item \textbf{Array}: ordered and indexed collection, duplicates allowed.
\end{itemize}
\vspace{11pt}

\newpage
\boldsecbottom{Collection Type --- Set}
\vspace{11pt}
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TYPE employeetype (
    ssn SMALLINT NOT NULL,
    fname CHAR(25) NOT NULL,
    lname CHAR(25) NOT NULL,
    empAddress international_address,
    ...
    empFingerprint fingerprint,
    photograph image,
    telephone SET (CHAR(12)),
    FUNCTION age(employeetype) RETURNS INTEGER
);

CREATE TABLE employee OF TYPE employeetype(PRIMARY KEY ssn);

SELECT ssn, fname, lname
FROM employee
WHERE '2123375000' IN (telephone)
\end{lstlisting}
\vspace{11pt}

\boldsec{Physical Concepts}

A \textbf{data item (or field)} is a collection of bits or characters representing a single value on storage medium. A \textbf{stored record} is the physical representation of a tuple in a relational table.

A \textbf{physical file} implements a relational table by storing its records. In most cases, all records in a file share the same structure. In some situations, however, records representing different real-world entities may be stored together.

A \textbf{physical database} is an integrated collection of physical files.

\subsection{Record Organization}
\vs

\textbf{Record Organization} defines how data items are arranged into physical records. Each \textbf{data item} is stored as a sequence of bits. The format depends on the attribute's data type (e.g., numeric, character, date/time, BLOB, CLOB).

Common record organization techniques include
\begin{itemize}
    \item Relative Location
    \item Embedded Identification
    \item Pointers and Lists
\end{itemize}
\vs

\boldsec{Record Organization --- Relative Location}

\textbf{Relative location} is the simplest and most widely used record organization technique. Records store only attribute values, placed at \textbf{fixed, continuous locations}. Attributes of the same entity are stored at \textbf{physically adjacent addresses}.

Attribute identifiers (types) and meanings are determined by their \textbf{fixed relative positions}.

Example: \texttt{EMPLOYEE(SSN, name, address, \dots)}

\img[0.7]{34.jpg}

\boldsecbottom{Record Organization --- Embedded Identification}

In \textbf{Embedded Identification}, each attribute value is \textbf{preceded by its attribute identifier (type)}. Attributes do \textbf{not need a fixed order} within a record. In fact, only non-empty attributes are stored.

This option provides flexibility for \textbf{optional and variable-length attributes}. It is conceptually similar to XML and JSON representations.

\img[.9]{35.jpg}

\boldsecbottom{Record Organization --- Pointers and Lists}

\textbf{Pointers and lists} support \textbf{variable-length and repeating attributes}. This is well-suited for: variable-length data types, multi-valued attributes, and optional attributes.

Example: A person may have multiple addresses.

\img[0.7]{36.jpg}

This technique is commonly used for BLOB and CLOB attributes. Large objects are stored separately, with records containing \textbf{pointers} to their locations.

\boldsec{Dealing with Variable-Length Records}

Variable-length records can also be handled using \textbf{delimiters} between attributes. Delimiters explicitly mark \textbf{attribute boundaries}.

This is common in text-based and semi-structured data formats (e.g., CSV, JSON, and XML). It is simple to implement, but it may incur parsing overhead.

\img[0.7]{37.jpg}

\boldsecbottom{Example: Oracle Physical Record Structure}

\img[0.6]{38.jpg}

Each row begins with a \textbf{row header}. The row header stores metadata such as:
\begin{itemize}
    \item \textbf{Row pieces} (row rows spanning multiple blocks).
    \item \textbf{Chaining information} (for chained row pieces)
    \item \textbf{Number of columns} in the row piece
    \item \textbf{Cluster keys} (for clustered tables only)
\end{itemize}
\vs

\boldsecbottom{Disk Block (Disk Page) and Blocking Factor}

A \textbf{disk block} (also called a \textbf{disk page} or cluster) is the basic unit of data transfer between disk storage and main memory. Each disk block consists of \textbf{multiple contiguous disk sectors}.

The \textbf{blocking factor (BF) } is the \textbf{number of records stored in a single block}. Since a DBMS reads and writes data \textbf{one block at a time}, the blocking factor determines how many records are retrieved per disk I/O operation.

Blocking Factor Calculation, for fixed-length records: $BF = [\frac{BS}{RS}]$ where BS: block size (bytes), RS: record size (bytes).

For \textbf{variable-length records}, BF represents the \textbf{average number of records per block}, rather than an exact value.

\boldsec{Oracle Data Block Structure}

\img[0.3]{39.jpg}

\textbf{Header (Common and Variable)}: The header contains general block information, such as the block address and the type of segment (for example, data or index).

\textbf{Table Directory}: This portion of the data block contains information about the table having rows in this block.

\textbf{Row Directory}: This portion of the data block contains information about the actual rows in the block (including addresses for each row piece in the row data area). After the space has been allocated in the row directory of a data block's overhead, this space is not reclaimed when the row is deleted. Therefore, a block that is currently empty but had up to 50 rows at one time continues to have 100 bytes allocated in the header for the row directly. Oracle reuses this space only when new rows are inserted into the block.

\textbf{Overhead}: The data block header, table directory, and row directory are referred to collectively as overhead. Some block overhead is fixed in size; the total block overhead size is variable. On average, the fixed and variable portions data block overhead total 84 to 107 bytes.

\textbf{Row Data}: This portion of the data block contains table or index data. Rows can span blocks.

\textbf{Free Space}: Free space is allocated for insertion of new rows and for updates to rows that require additional space (for example, when a trailing null is updated to a nonnull value). Whether issued insertions actually occur in a given data block is a function of current space in that data block and the value of the space management parameter \texttt{PCTFREE}. In data blocks allocated for the data segment of a table or cluster, or for the index segment of an index, free space can also hold transaction entries. A \textbf{transaction entry} is required in a block for each INSERT, UPDATE, DELETE, and SELECT...FOR UPDATE statement accesses one or more rows in the block. The space required for transaction entries is operating system dependent; however, transaction entries in most OS require approximately 23 bytes.

\subsec{File Organization}

\boldsecbottom{Search Key}

A \textbf{search key} is one or more attributes used to \textbf{retrieve records}. It defines \textbf{selection criteria}, not uniqueness. A search key is \textbf{not necessarily a key} (i.e., it may not uniquely identify a record).

Properties of a Search key include:
\begin{itemize}
    \item Can be: A \textbf{primary key}, an \textbf{alternative key}, or one or more \textbf{non-key attributes}.
    \item Can be \textbf{composite}, e.g., (Country, Gender)
    commonly used for \textbf{range queries} (e.g., YearOfBirth BETWEEN 1980 AND 1990)
\end{itemize}

\boldsec{Category of File Organization Methods}

\textbf{Primary File Organization} Methods determine the physical placement of records on storage media. They define how records are initially stored. For example, Heap file organization, sequential file organization, and hash file organization.

\textbf{Secondary File Organization} Methods provide \textbf{efficient access paths} for retrieval. They use a \textbf{search key} not used in the primary organization. Secondary File Organization is typically implemented using \textbf{secondary indexes}.

\boldsec{Primary File Organization Methods --- Heap File Organization}

\textbf{Heap file} is the simplest \textbf{primary file organization}. New records are \textbf{appended to the end of the file}. There is \textbf{no relationship} between record values and physical storage location.

In Heap File Organization, \textbf{insertion} is efficient, but \textbf{retrieval} requires linear search.

The Retrieval Performance for a file with $NBLK$ blocks, the average block accesses for a\textbf{ unique search}:

\myeq{\frac{NBLK}{2}}

For a non-unique search key, \textbf{the entire file (NBLK) must be scanned}.

\boldsec{Example: Oracle Heap-Organized Table}

In Oracle, the default file organization is a heap file. In a heap organized table, rows are stored in no particular order on disk. Additionally, new rows are paced wherever space is available.

By default, \texttt{CREATE TABLE} creates a heap-organized table

\vs
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TABLE t1 (c1 NUMBER, c2 VARCHAR2(30));

-- The heap organization can also be specified explicitly:

CREATE TABLE t1 (c1 NUMBER, c2 VARCHAR2(30)) ORGANIZATION HEAP;
\end{lstlisting}
\vs

\boldsec{Primary File Organizations Methods -- Sequential File Organization}

In Sequential File Organizations, records are stored in sorted order (ascending or descending based on a search key). The search key is often the primary key, but may also be a non-key attribute, or a composite attribute.

The advantage of this method is the high efficiency for ordered retrieval and range queries.

\img[0.3]{40.png}

Records can be retrieved using linear search ($O(n)$) or Binary Search ($O(nlogn)$) (on the ordered file). Binary search repeatedly halves the search interval. The retrieval performance (expected block accesses) of a linear search is

\myeq{\frac{NBLK}{2} * sba}

where sba is sequential block access and NBLK is the number of blocks in a file. For Binary Search:

\myeq{log_2(NBLK) * rba}

where rba is random block access.

\newpage

\boldsecbottom{Example - Sequential File Organization}

Blocking factor: $BF=[BS/RS] = [2048/100] = 20$ records per block.

Number of blocks in data: $NBLK=30000/20=1500$ blocks.

If a single record is retrieved according to primary key using linear search, expected number of required block accesses is $1500/2=750$ sba (sequential block access).

If binary search is used, the expected number of block accesses is $log_2(1500) \approx 11$ rba (random block access).

\boldsec{Primary File Organization Methods --- Random File Organization}

Hash file organization establishes a direct relationship between a search key value and a record's physical location. A hash function maps a key value to a storage address. Records are accessed using \textbf{random (direct) access}, not ordering.

The insertion process applies a hash function to the record's key and then stores the record at the resulting physical address. The retrieval process applies the same hash function to the search key and then directly accesses the block where the record is stored.

\boldsec{Key-to-Address Transformation}

\img[0.6]{41.png}

\boldsecbottom{Key-to-Address Transformation}

The search key value (numeric or alphanumeric) is first converted into an integer. A hashing algorithm it then applied to compute an address. A common hashing algorithm is the division method:

\myeq{address(key_i)=key_i\mod M}

where $M$ is typically a prime number, slightly larger than the number of available addresses. The hash value identifies a \textbf{bucket} (a continuous area of record addresses). The bucket address is translated into a physical disk block address.

\boldsec{Illustration: Record Retrieving Using Hashing}

A query specifies a search key value (e.g., \texttt{department\_id} = 20). The DBMS applies the same hash function used during insertion and the hash value maps the key to a specific bucket. The bucket then corresponds to a physical disk block. The DBMS directly access the block to retrieve the record(s).

\img[0.7]{42.png}

The key idea is applying the \textbf{same hash transformation} to the search key yields the storage address of the record.

\boldsec{Hashing and Collisions}

The purpose of hashing is to \textbf{evenly distribute} all keys across the available address space. However, multiple records with the same hash value may be assigned to the \textbf{same bucket}, leading to a \textbf{collision}.

When this happens, the bucket is said to be in overflow.

\img[0.7]{43.png}

\boldsecbottom{Hash File Organization Performance}

For a non-overflow record retrieval, 1 rba (random block access) is added to the bucket's first block. This can possibly be followed by 1 or more sba (sequential block accesses) within the bucket.

Hash file organization is \textbf{highly efficient} for \textbf{equality-based searches} on the search key.

\textbf{Overflow records} may require additional block accesses, which depends on: percentage of overflow records and the overflow handling technique used.

\boldsec{Indexed Sequential File Organization}

Indexed Sequential File Organization is where records are stored in stored (sequential) order based on a search key. One or more indexes are built on the search key. 

This method supports:
\begin{itemize}
    \item Equally search (via index).
    \item Range search (via sequential order).
\end{itemize}
\vs

This method also combines the strengths of \textbf{sequential files} and \textbf{index-based access}.

\img[0.9]{44.png}

\boldsecbottom{Index Entry Structure}

An \textbf{index entry} stores the \textbf{search key value} of the first record in the interval, as well as a \textbf{pointer} to the physical location of that record.

The index entry format:

\texttt{Index Entry = <search key value, block pointer or record pointer>}

Examples: \texttt{<7788,pointer>,<(1980,M), pointer>}

\vs
Index entries are \textbf{much smaller than data records}, enabling efficient searching.

As a result, the index is smaller than many other index structures.

\boldsecbottom{Multilevel Indexing}

In a single-level index, as the data size increases, the index itself may become too large to be searched efficiently. To improve search efficiency, an index-to-the-index is introduced. \textbf{Multilevel indexes} help optimize indexing by \textbf{organizing index entries hierarchically}, making searches more efficient.

A \textbf{search tree} is used to locate a record based on the value of one of its fields. A \textbf{multilevel index} structures the index entries using a search tree. The performance improvement achieved with high-level indexes comes from the fact that each index level is searched efficiently using a search tree retrieval technique.

\vs
Example: Multilevel Index

\img[0.8]{50.png}

Each \textbf{index block} represents a node in the tree. Each \textbf{index entry} in an \textbf{internal node} consists of a \textbf{search key value and a reference} to the corresponding block (node) in the lower-level index. 

Each access to the index leads to navigation down a sub tree, thereby narrowing the search interval. The \textbf{lowest-level index entries}, located in the leaf node, \textbf{contain pointers to disk blocks or individual records}.

\boldsec{Types of Multilevel Index (Tree Index)}

There are various types of multi-leveled indexes, including:
\begin{itemize}
    \item B-Tree
    \item B+Tree
    \item B*Tree
    \item Quadtree
    \item R-Tree
    \item R+tree, etc.
\end{itemize}
\vs

Among these, \textbf{B-tree} and \textbf{B+tree} index structures are widely used for traditional data types (such as char, VARCHAR, date, and number) in many commercial database products.

\boldsec{B-Tree}

\textbf{B-Tree} is a variation of search trees, where each node corresponds to a disk block and nodes are kept between half fill and full to cater for accommodating changes in the data file without the need for too extensive rearrangements of the index.

Every node contains a set of search key values, a set of tree pointers that refer to child nodes, and a set of data points that refer to data records or blocks with data records, that correspond to the search key values.

A B-tree is a \textbf{balanced tree}; all leaf nodes are at the same level in the tree.

Most DBMS implementations use indexes based on B+-trees rather than B-trees.

In a B+-tree, only the leaf nodes contain data points. All key values that exist in the non-leaf nodes are repeated in the leaf nodes, such that every key value occurs in a leaf node, along with a corresponding data pointers. Every leaf node also has one tree pointer, pointing to its next sibling or two tree pointers, pointing to its previous and next siblings.

\boldsec{Characteristics of B+ Trees}

B+ Trees are the most widely used tree index. They are more flexible and have a dynamic structure that adjusts inserts and deletes. The height of B+-tree is often smaller, resulting in less block accesses to search. Additionally, Non-leaf nodes do not contain data points.

Leaf nodes have an entry for every value of the search field. The tree is always balanced (height-balanced). Leaf nodes are linked using (tree) page pointers. Lastly, B+Trees support equality and range-searches efficiently.

\subsec{Physical Database Organization}

\boldsecbottom{Physical Database Design}

The purpose of the physical database design is to translate a logical data model into an internal data model (the logical description of data into technical specifications for storing and retrieving data) and design indexes to speed up data access.

This is a joint responsibility of the database designer and the DBA. Here, we focus on the generic file organization principles are implemented in particularly a relational DBMS.

\vs
\begin{aside}
    \textbf{Note:} SQL does not impose any standardization on the internal data model or on the way in which a logical relational data model is implemented physically. Different DBMS vendors all have their own approaches.
\end{aside}
\vs

\boldsecbottom{Databases}

User databases have a physical structure that is determined by the database designer and contain data that represents an organization's state. A \textbf{physical user database} is a collection of index files and data files, organized according to the principles of record organization and file organization.

In system databases, the system database's structure is predefined by the database vendor and holds the catalog tables that support the DBMS's exploitation.

\newpage
\boldsecbottom{From Database to Tablespace}

Many DBMS implementations introduce an additional level of indirection between a logical database and the physical data files, called a \textbf{tablespace}.

A tablespace can be considered as a physical container of database objects. It consists of one or more physical files, possibly distributed over multiple storage devices. Every logical table is assigned to a tablespace to be persisted physically a (stored table). A stored table occupies one or more disk blocks or pages in the tablespace.

A tablespace can contain indexes as well (index spaces are used for this purpose).

\img[0.5]{57.jpg}

\boldsecbottom{Decisions}

There is a wide choice of storage devices. On the chosen storage devices, files are created that form the tablespaces (and index spaces). Tables then belong to a tablespace. If desired, tables can be distributed over multiple physical files.

Indexes are assigned to tablespaces or to separate indexed spaces. A primary or clustered index determines the physical ordering of the data records in a file. So creation or deletion of such an index deserves particular consideration.

\boldsecbottom{Data Blocks, Extents, and Segments}

\img[0.35]{60.jpg}

Oracle Database allocates logical database space for all data in a database. The units of database space allocation are \textbf{data blocks, extents, and segments}.

At the finest level of granularity, Oracle Database stores data in data blocks (also called logical blocks, Oracle blocks, or pages. One data block corresponds to a specific number of bytes of physical database space on disk.

The next level of logical database space is an extent. An extent is a specific number of contiguous data blocks allocated for storing a specific type of information. 

The level of logical database storage greater than an extent is called a segment. A segment is a set of extents, each of which has been allocated for a specific data structure and all of which are stored in the same tablespace. For example, each table's data is stored in its own \textbf{data segment}, and each index's data is stored in its own \textbf{index segment}. If the table or index is partitioned, each partition is stored in its own segment. When the existing extents of a segment are full, the DBMS allocates another extent for that segment. The extents of a segment may or may not be continuous on disk.

\boldsec{Storage Parameters in Oracle}

\begin{itemize}
    \item \texttt{INITIAL}: The size, in bytes, of the first extent allocated when a segment is created. This parameter cannot be specified in an ALTER statement.
    \item \texttt{MINEXTENTS}: The total number of extents to be allocated when the segment is created. This allows for a large allocation of space at creation time, even if contiguous space is not available.
    \item \texttt{EXTENTS}: The total number of extents, including the first, that can ever be allocated for the segment.
\end{itemize}
\vs

\boldsecbottom{Storage Parameters in Oracle (Continued)}

\begin{itemize}
    \item \texttt{NEXT}: The size, in bytes, of the next incremental extent to be allocated for a segment. The second extent is equal to the original setting for NEXT. From there forward, NEXT is set to the previous size of NEXT multiplied by (1 + PCTINCREASE/100).
    \item \texttt{PCTINCREASE}: The percentage by which each incremental extent grows over the last incremental extent allocated for a segment. If 0, then all incremental extents are the same size. If greater than zero, then each time NEXT is calculated, it grows by PCTINCREASE. The new NEXT is rounded up to the next multiple of a block size.
\end{itemize}
\vs

\boldsecbottom{Example: Specifying Table Storage}

\vs
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE TABLE divisions (
div_no NUMBER(2),
div_name VARCHAR2(14),
location VARCHAR2(13)
)
STORAGE (INITIAL 100k NEXT 50K MINEXTENTS 1 MAXEXTENTS 50 PCTINCREASE 5)
\end{lstlisting}
\vs

Note that each additional NEXT extent is ~5\% larger than the previous.

\boldsec{Free Space Management of Data Block in Oracle}

\img[0.8]{61.jpg}

\begin{itemize}
    \item \texttt{PCTFREE}: Set the minimum percentage of a data block to be reserved as free space for possible updates to rows that already exist in that block.
    \item \texttt{PCTUSED}: Set the minimum percentage of a data block that can be used for the row data plus overhead before new rows are added to the block.
\end{itemize}

Even though most DBMSs provide ample auto-configuring and self-tuning features, you (DBA) can set storage parameters for various data structures, such as
\begin{itemize}
    \item Tablespace (used as storage parameter defaults for all segments).
    \item Tables, partitions, clusters, materialized views, and materialized view logs (data segments).
    \item Indexes (index segments).
    \item Rollback segments.
\end{itemize}

\newpage
\boldsecbottom{CASE Example}

\textbf{Case 1}: Common activity includes UPDATE statements that increase the size of the rows. Settings: \texttt{PCTFREE=20,PCTUSED=40}. PCTFREE is set to 20 to allow enough room for rows that increase in size as a result of updates. PCTUSED is set to 50 so that less processing is done during high update activity, thus improving performance.

\textbf{Case 2}: Most activity includes INSERT and DELETE statements, and UPDATE statements that do not increase the size of affected rows. Settings: \texttt{PCTFREE=5,PCTUSED=60}. PCTFREE is set to 5 because most UPDATE statements do not increase row sizes. PCTUSED is set to 60 so that space freed by DELETE statements is used soon, yet processing is minimized.

Case 3: The table is very large, and storage is a primary concern. Most activity includes read-only transactions. Settings: \texttt{PCTFREE=5, PCTUSED=40}. PCTFREE is set to 5 because this is a large table, and you want to completely fill each block.

\subsec{Index Design}

\boldsecbottom{Index}

Indexes are one of the most important performance-tuning tools available to database designers and administrators. An index provides an efficient path to table data by reducing the number of disk I/O operations required. 

The presence (or absence) of indexes directly influences the query optimizer's choice of execution plan. Proper index design is a critical component of physical database design.

\boldsec{Index Design}

\begin{itemize}
    \item \textbf{What indexes} should we create? Which relations (tabes) should have indexes? What attribute(s) should be used as search keys? Should we create multiple indexes on the same table?
    \item \textbf{What kind of index} should each be? Clustered or non-clustered? Tree or hash? Unique or non-unique? Single attribute or composite?
\end{itemize}
\vs

\boldsecbottom{Index Creation}

There is no fully standardized SQL syntax for index creation. However, most DBMSs support a similar general syntax.

\vs
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE [UNIQUE] INDEX index_name
ON table_name (column_name [ASC/DESC] {, column_name[ASC|DESC]})
\end{lstlisting}
\vs

Examples:

\vs
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE UNIQUE INDEX prodnr_index
ON product(prodnr ASC);

CREATE INDEX productdata_index
ON product(prodprive DESC, prodtype ASC);

CREATE INDEX prodname_index
ON product(prodname ASC)
CLUSTER; -- Index for cluster key data in Oracle
\end{lstlisting}
\vs

\boldsecbottom{[Note] Index Syntax is DBMS-Specific}

SQL syntax for index creation is similar across systems, but many options are vendor-specific. In particular, clustered index syntax differs significantly among DBMSs. Always check the specific DBMS documentation when designing an index.

Examples:

SQL Server
\vs
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE CLUSTERED INDEX index_name
ON table_name (column_name);
\end{lstlisting}
\vs

Oracle does not use \texttt{CREATE CLUSTERED INDEX}. Instead, it supports Index-Organized Tables (IOT), Cluster objects, and storage and tablespace options.

PostgreSQL uses \texttt{CLUSTER table\_name USING index\_name}

MySQL(InnoDB - a storage engine used by MySQL) --- The primary key is clustered automatically, and the secondary indexes are non-clustered.

\boldsec{Reasons for Index Creation}

Index creation enables efficient retrieval of rows based on specific queries or selection criteria. It also enables efficient execution of join queries and enforces uniqueness on a column value or on a combination of column values.

Index creation allows logical ordering of rows in a table and physical ordering of rows in a table.

\boldsec{Reasons for Index Creation --- Efficient Retrieval}

Indexes improve query performance by providing efficient access paths to rows that satisfy selection conditions.

Retrieval is significantly faster when search attributes are indexed. Selection criteria targeting a unique tuple can be supported by a primary index or a unique secondary index on a candidate key. Selection criteria targeting a set of tuples can be supported by a clustered index (efficient for range retrieval) or a secondary index on a non-key attribute type of composite attributes.

Composite indexes can improve performance when query predicates match the index's leading attributes.

\boldsec{[Note]: Query with a Composite Index}

For B+ tree composite indexes, the leftmost prefix rule applies.

Examples:
\begin{itemize}
    \item An index on $(A,B,C)$ supports the select conditions with $A$, $(A,B)$, and $(A,B,C)$.
    \item It does NOT efficient support $B$ alone, $C$ alone, or $(B,C)$.
\end{itemize}
\vs

So performance improvement depends on \textbf{predicate alignment with index order}.

\boldsec{Reasons for Index Creation: Efficient Join}

Indexes improve the \textbf{performance of join} operations.

Join processing is often one of the most expensive operations in query execution. Indexes can accelerate joins by enabling efficient lookup of matching tuples in one or both participating tables. Indexes may reduce join cost from $O(N*M)$ to $O(NlogM)$ depending on join algorithm and selectivity.

Index are particularly useful for Nested-loop joins (index lookup on inner relation) and foreign key - primary key joins.

\textbf{Foreign key attributes are often indexed} to improve join performance and maintain referential integrity.

\boldsec{Reasons for Index Creation: Enforcing Uniqueness}

An index can be created to enforce uniqueness on a column or combination of columns. When a uniqueness constraint exists, the DBMS uses a unique index to efficiently enforce the constraint by checking only the index entries for duplicate values (i.e. if the value is already in the index, the DBMS rejects the operation with a uniqueness/constraint violation. On the other side, if the value is not in the index, it is safe to insert, and the index is updated).

A unique index is automatically created for every primary key. A unique index is also automatically created for attributes declared with a UNIQUE constraint in CREATE TABLE. The database designer may explicitly create a UNIQUE INDEX on other candidate keys to enforce uniqueness.

\boldsec{Reasons for Index Creation: Logical Ordering}

Indexes provide logical ordering of rows. Every index maintains entries in a defined order (ACS or DESC). This ordering supports efficient processing of GROUP BY, ORDER BY, and Range Queries.

Secondary indexes allow multiple logical orderings on the same table, even if the table itself is not physically ordered on those attributes. Only a \textbf{clustered index} (or index-organized table) affects the physical ordering of the table data.

\boldsec{Reasons for Index Creation: Physical Ordering}

Physical ordering of rows in a table can be determined by a clustered index. The ordering of the index entries may determine the physical storage order of table rows. When the index defines the physical layout of the table, it is called a \textbf{clustered index} (modern terminology).

\textbf{Only one index for each table} can determine the physical ordering of rows. Range queries on the clustered keys are highly efficient because matching rows are stored close together. The choice of clustering attribute(s) must be made carefully, based on expected query workload.

\vs
\boldsecbottom{Dense vs. Sparse Index}

A \textbf{Dense Index} contains an index entry for every search key value (or every value). Each index entry points directly to the corresponding record. This provides fast lookup due to direct access but requires more storage space. This is commonly used for secondary indexes.

A \textbf{Sparse Index }contains index entries for only some search key values. Typically, one index entry per data block (points to first record in the block). This requires teh data file to be physically ordered on the search key. This uses less storage space, but lookup may require additional sequential scanning with a block.

\boldsec{More about Index}

Only one clustered index (and primary index with physical ordering) can exist per table. A table may have multiple secondary (non-clustered) indexes. Secondary indexes can be created or dropped without modifying the actual table data.

This illustrates \textbf{physical data independence}: Indexes can be added or removed without changing the logical schema or application programs.

\boldsec{Cost of Indexes}

Index consumes additional storage capacity. Index maintenance also adds overhead to data modification operations such as INSERT, UPDATE, and DELETE. Every modification of indexed attributes requires corresponding updates to the index structure. However, indexes can improve the row-selection phase of UPDATE and DELETE statements.

\subsec{General Index Design Guidelines}

\textbf{Good candidates for indexing} include primary keys and other candidate keys (to enforce uniqueness). Foreign keys (to improve join performance) are also good candidates. Finally, attributes that are frequently used in join conditions, in WHERE clauses, and in ORDER BY or GROUP BY clauses.

\textbf{Attributes to avoid} include large or variable-length attributes (e.g., long VARCHAR, large text fields). Low-selectivity attributes (few distinct values). Finally, attributes in very small tables (full scan may be cheaper).

As for \textbf{Workload consideration}, indexes improve retrieval performance but can increase overhead for INSERT, DELETE, and UPDATE operations. Index design must balance read frequency vs. write frequency.

\boldsec{Guide for Index Design and Tuning}

\begin{itemize}
    \item Guideline 1: \textbf{Whether to Index}: Do not build an index unless a query can benefit from it. Avoid unnecessary indexes --- They increase storage and maintenance overhead. Index decisions should be workload-driven.
    \item Guideline 2: \textbf{Choice of Search Key}: Index attributes that frequently appear in WHERE clauses, Join conditions, and ORDER BY or GROUP BY clauses. Consider selectivity and query frequency.
    \item Guideline 3: \textbf{Primary Keys and Foreign Keys}. Index every primary key (usually created automatically), and index most foreign keys to improve join performance. Most joins occur between primary key and foreign key attributes. Finally, for very small tables, a full table scan may be cheaper than using an index.
\end{itemize}
\vs

\boldsecbottom{Multi-Attribute Search Keys [Guideline 4]}

More than one attribute of a relation in WHERE. It is an Index-only strategy. Avoid retrieving tuples from relations. For example, suppose \texttt{D.dno} has an index and \texttt{E.dno} has an index. There is no need to access the employee data file.

\vs
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
SELECT D.mgr
FROM Emp E, Dept D
WHERE E.dno = D.dno
\end{lstlisting}
\vs

No attributes of Employee are retained, compared with

\vs
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
SELECT D.mgr, E.eid
FROM Emp E, Dept D
WHERE E.dno = D.dno
\end{lstlisting}
\vs

\textbf{E.g., No need to access both Employee and Dept data files}. While this is very useful, do not overuse with making many extremely query-specific indexes.

\vs
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
SELECT D.dno
FROM Emp E, Dept D
WHERE D.dno = D.dno
\end{lstlisting}
\vs

\boldsecbottom{Avoid Index with Value Distribution that are Extremely Skewed [Guideline 5]}

Don't allow just a few index values to have much higher levels of frequency than other values. When index values have a highly uneven frequency distribution, the index becomes less effective.

For example, if an index were created on a gender column in a database where the number of males is vastly greater than females, the index would be inefficient.

\boldsec{Hash vs. Tree Index [Guideline 6]}

A \textbf{tree index} (B+ Tree) is usually preferable because it supports range query as well as equality query. It is used for column comparisons in expressions that use the $=,>,\geq, <,\leq$, BETWEEN AND, or LIKE.

A \textbf{hash index} is better for a very important equality ($=$), no range queries. It is used only for equality comparisons that use the $=$.

\boldsec{Whether to Cluster [Guideline 7]}

Choose carefully the clustered index for each table. A cluster index dictates how data is to be physically stored for a specific table. Any other index on that table cannot be a clustered. index.

Create a clustered index on the most important query. This is particularly efficient on columns that are often searched for ranges of values (BETWEEN, <, >) since data in table is physically sorted on that column. It is good to build a clustered index on a primary key with range searches.

In MS SQL Server or Sybase case, a PRIMARY KEY constraint creates a \textbf{clustered indexes by default} if no clustered index already exists on the table. If a clustered index already exists, the primary key is created as non clustered. 

Example: Non clustered primary key in MS SQL Server

\vs
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
Create Table Customer (
    CustID number primary key nonclustered,
    ...
);
\end{lstlisting}
\vs

\boldsec{Balancing the Cost of Index Maintenance [Guideline 8]}

Use attributes for indexes with caution when they are frequently updated. maintaining an index can slow down frequent update operations. Kep in mind, however, index may speed up an update or delete operation.

E.g., Increase the salary of a given employee id when id has an index.

\vs
\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
UPDATE employee
SET salary = salary * 1.1
WHERE id = '7788';
\end{lstlisting}
\vs

Avoid or remove redundant indexes.

\boldsec{Perform Regular Index Maintenance [Guideline 9]}

Index structures require maintenance as tables undergo INSERT, DELETE, and UPDATE. Frequent modifications may cause fragmentation, page splits, and reduced performance. Maintenance Operations may rebuild indexes, reorganize indexes (de-fragment), and update index statistics. \textbf{Indexes can be dropped and rebuilt when necessary}.

\subsec{Supplementary Guidelines for Application-Specific Indexes in Oracle}

In Oracle, you create the indexes after inserting table data. At that point, you can index the correct tables and columns.

As a rule of thumb, create an index if you frequently want to retrieve less than 15\% of the rows in a large table. Index columns are used for joins to improve performance on joins of multiple tables. \textbf{Primary and unique keys automatically have indexes, but you might want to create an index on a foreign key}. Finally, small tables do not require indexes.

Some columns are strong candidates for indexing.
\begin{itemize}
    \item Values are relatively unique in the column.
    \item There is a wide range of values (good for regular indexes).
    \item There is a small range of values (good for bitmap indexes).
    \item The column contains many nulls, but queries often select all rows having a value.
\end{itemize}
\vs

Columns with the following characteristics are less suitable for indexing:
\begin{itemize}
    \item There are many nulls in the column and you do not search on the non-null values.
\end{itemize}
\vs 

It is also important to limit the number of indexes for each table. The more indexes, the more overhead is incurred as the table is altered. Finally, you should choose the order of columns in composite indexes. The order of columns in the CREATE INDEX statement can affect query performance. In general, put the column expected to be used most often \textbf{first} in the index.

\subsec{Table Clustering}

\textbf{Table clustering} in a relational database system refers to \textbf{the storage of related data from multiple tables in the same database blocks}. This technique is used to improve the efficiency of data retrieval operations, especially when performing joins on tables that are often accessed together.

\newpage
\boldsecbottom{Unclustered vs. Clustered Tables}

\img[0.6]{64.jpg}

\boldsecbottom{Key Concepts in Table Clustering}

\begin{itemize}
    \item \textbf{Cluster}: A cluster is a schema object that contains data from one or more tables that are related based on common columns. These common columns are typically the columns on which tables are joined.
    \item \textbf{Cluster Key}: The cluster key is the column or set of columns that the tables in the cluster have in common. Rows with the same cluster key value from all the clustered tables are stored together in the same blocks.
    \item \textbf{Hash Clusters}: RDBMS such as Oracle also supports hash clusters, where a hash function is used to determine the database block in which the rows are stored. This can provide very efficient retrieval for equality searches based on the hash key.
\end{itemize}

\boldsec{Advantages of Table Clustering}

\begin{itemize}
    \item \textbf{Improved Disk I/O}: Clustering related rows reduces the number of disk reads required to fetch the data.
    \item \textbf{Join Efficiency}: Since related rows from different tables are stored close together, joins on clustered tables can be faster.
    \item \textbf{Data Cohesion}: Clustering maintains the logical cohesion or related data, which can make application development more intuitive.
    \item \textbf{Less Storage}: Less storage is required to store related table and index data because the cluster key value is not stored repeatedly for each row.
\end{itemize}
\vs

\boldsecbottom{Example: Table Clustering in Oracle}

Here are the steps:

\vs
\begin{itemize}
    \item \textbf{Define a Cluster}: Use the \texttt{CREATE CLUSTER} statement to define a cluster by specifying its name, the cluster key, and its storage characteristics.
    \item \textbf{Add Tables to Cluster}: Use the \texttt{CREATE TABLE} statement with the CLUSTER clause to create tables within the defined cluster.
    \item \textbf{Load Data}: Insert data into the clustered tables. Oracle will automatically store rows with the same cluster key value together.
    \item \textbf{Gather Statistics}: Use Oracle's \texttt{DBMS\_STATS} package to gather statistics on the cluster for the optimizer.
    \item \textbf{Monitor Performance}: Regularly monitor the performance to ensure that clustering is providing the desired benefits.
\end{itemize}
\vs

\begin{lstlisting}[language=sql, breaklines=true, showstringspaces=false]
CREATE CLUSTER employee_cluster (department_id NUMBER) STORAGE (INITIAL 10K NEXT 10K);

CREATE TABLE employee (
    employee_id NUMBER,
    department_id NUMBER,
    name VARCHAR2(100)
) CLUSTER employee_cluster (department_id);

CREATE TABLE departments (
    department_id NUMBER,
    department_name VARCHAR2(100)
) CLUSTER employee_cluster (department_id);

EXEC DBMS_STATS.gather_table_stats('SCOTT', 'employees', 'employee_cluster');
\end{lstlisting}
\vs

\boldsecbottom{Considerations for Implementation}

\textbf{Access Patterns}: Clustering is beneficial when tables are often joined on the cluster key. It's less useful if tables are typically accessed independently. \textbf{Cluster Key Choice} is also important since the columns chosen as the cluster key should be such that \textbf{the related rows actually need to be retrieved frequently together}. Finally, clusters can require more \textbf{maintenance} than non-clustered tables, as updates to the cluster key may necessitate moving data between blocks.

\boldsec{When Not to Use Table Clustering}

If tables are \textbf{frequently updated}, clustering can decrease performance because it may necessitate moving rows to maintain cluster integrity. 

If tables require frequent \textbf{full table scans}, clustering can lead to less efficient table scans since it groups row based on the cluster key.

Finally, \textbf{tables that require truncating} where truncating a table usually means quickly removing all rows. In clustered table, because rows are grouped by with related data from other tables, truncating operations may become complex or restricted.
